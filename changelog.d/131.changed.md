Streaming runs (`POST .../runs/stream`) now execute in a server-side task and honour `on_disconnect`: with the default `"continue"` a client disconnect no longer cancels the run, even while it is still queued (it keeps running and can be joined); pass `on_disconnect: "cancel"` for the old behaviour. As tasks, streaming runs can now be cancelled via `POST .../runs/{run_id}/cancel`, awaited via `GET .../runs/{run_id}/join`, and superseded by the `interrupt`/`rollback` multitask strategies (a streaming run superseded while still queued gets `409`). A cancelled streaming run ends with an `end` event whose `status` is `interrupted`.
